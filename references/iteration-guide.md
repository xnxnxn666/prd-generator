# Iteration Guide

When a user wants to modify an existing PRD (generated by this skill or otherwise), this guide governs the process. The core rule: never overwrite the old PRD.

## Version Management

### Directory naming

- First generation (greenfield or retrospective): `<project-name>-prd/`
- First iteration: `<project-name>-prd-v2/`
- Second iteration: `<project-name>-prd-v3/`
- And so on — auto-increment by scanning existing directories

When generating output, scan the working directory for existing `<project-name>-prd*` directories. Find the highest version number. The new output goes to the next version. If only `<project-name>-prd/` exists (no version suffix), the new one is `<project-name>-prd-v2/`.

### Backup warning (mandatory)

Before generating any iteration output, you MUST display this warning:

> Before I generate the new PRD, please manually back up your old PRD if you haven't already. For example:
> `cp -r <project>-prd <project>-prd-backup`
>
> I will generate the new version in a separate directory — your old PRD won't be touched. But it's always safer to have your own backup.

Do NOT run the backup command automatically. The user decides how and where to back up.

## Entry Detection

Iteration mode triggers when any of these conditions are true:

1. User explicitly says "update the PRD", "modify the spec", "iterate on the PRD", "改一下需求", etc.
2. CWD contains a `*-prd/` directory AND the user says something about changing/adding/removing features
3. CWD has `.interview-state.json` with `status: "complete"` AND the user indicates they want to revise

If the user's intent is ambiguous, offer the three options explicitly: "Are you starting a new project, analyzing an existing codebase, or revising a previous PRD?"

## Reading the Old PRD

Before asking any questions, read ALL files in the old PRD:

- `README.md` — project overview and module index
- Every file in `modules/` — feature specifications
- `user-journeys.md` — existing flows
- `data-model.md` — entities and relationships
- `integrations.md` — external dependencies
- `acceptance.md` — acceptance criteria
- `open-questions.md` — previously deferred decisions

Present a summary to the user before the interview:

> "Your current PRD at `<project>-prd/` defines **[N] modules** with **[X] P0 features**. The main modules are: [list]. The architecture is [pattern]. Ready to talk about what needs to change?"

## Change Interview

### Phase 1: Understand what's changing

Start open-ended: "What made you want to revise the PRD? What's changed since the last version?"

Listen for these categories and track them:

| Category | User says... | Action |
|---|---|---|
| **ADD** | "I need a notification system" | New module or feature within existing module |
| **REMOVE** | "We're dropping the chat feature" | Mark module/feature for removal |
| **MODIFY** | "Users should be able to..." (different from old spec) | Update existing module/feature |
| **REARCHITECT** | "We need to switch from monolith to microservices" | Rerun architecture assessment |
| **SCOPE CHANGE** | "This is now enterprise-only" or "We're simplifying for MVP" | Adjust target users, features, NFRs |

### Phase 2: Module-by-module review

Go through each existing module and ask:

- "Keep [module name] as-is?"
- "Keep but modify?" → What changes?
- "Drop entirely?"
- "Split into smaller modules or merge with another?"

### Phase 3: Gap analysis

After reviewing existing modules, ask:

- "What's completely new that wasn't in the old PRD?"
- "Are there edge cases you now realize we missed?"

For new features, run a lightweight Phase 2 interview (prioritize, check MVP boundary).

### Phase 4: Cross-check

Before finalizing:

1. **Dependency check** — If module A is being removed and module B depends on it, flag it: "Module B's [feature] depends on [removed feature]. What should we do?"
2. **Conflict check** — Run the conflict detection rules from `conflict-patterns.md` against the new combination of requirements. New additions can create new tensions.
3. **Architecture check** — If features were added or significantly changed, check whether the original architecture pattern still fits. Read `architecture-patterns.md` and recommend changes if needed.

## Output

### Change summary

Every iteration PRD MUST start with a change summary in its README.md:

```markdown
## Changes from v[N-1]

### Added
- [New module/feature] — reason

### Removed
- [Old module/feature] — reason

### Modified
- [Module/feature]: [what changed] — reason

### Unchanged
- [Key things that stayed the same]
```

### Module annotation in iteration output

For modified modules, use inline annotations:

- **[NEW]** — Didn't exist in previous version
- **[MODIFIED]** — Existed before but changed. Summarize what changed
- **[UNCHANGED]** — Carried over verbatim from previous version
- **[REMOVED in vN]** — If the module was removed, include a one-line note in the README index explaining why (don't keep the full spec)

### State file update

After generating iteration output, update `.interview-state.json`:

```json
{
  "mode": "iteration",
  "version": 2,
  "previous_version_dir": "xxx-prd/",
  "change_summary": ["added: notification module", "removed: chat module"],
  "status": "complete"
}
```

### Post-generation reminder

After generating, remind again:

> "New PRD generated at `<project>-prd-v2/`. Your old PRD at `<project>-prd/` is untouched. Make sure you've backed it up if needed."
